# The cache relay (-experimental-relay)

Written 2026-10-23.

## What it does

Claude Code marks for the cache only the system prompt and the last
messages. To keep the view's first part cached, opt-chat sends it as a
message of its own and waits for the model's "ok" (the ack): one extra
request per turn, and per compaction whose first message is not cached
yet.

With `-experimental-relay`, opt-chat starts a relay on a loopback port
with a random path and gives every `claude -p` call
`ANTHROPIC_BASE_URL` pointing at it. The relay forwards each request to
`https://api.anthropic.com` with its headers as they came. Only the body
of `POST /v1/messages` changes:

- The view's first block ends with `relayMark`. The relay puts a
  `cache_control` mark on that block, with the TTL of Claude Code's own
  marks.
- If that makes five marks, it drops the system prompt's earliest one,
  which the later marks cover. The API takes four.
- When Claude Code puts its environment block in a system message after
  the first user message, the relay splits that message after the mark,
  puts the system message there and an assistant "ok" after it. That is
  the layout the ack gave, with no model call. The API refuses a system
  message followed by a user message (400, checked).

The ack then sends nothing. The first message goes out with the rest of
the view in one message, and the calls waiting on its prefix go once that
response begins, as before.

The relay starts only when none of `ANTHROPIC_BASE_URL`,
`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` or the Bedrock, Vertex and
Foundry switches is set, so it never moves a call to another account or
to API billing. A body it can't parse, or one with no mark, goes on as it
came. `OPT_CHAT_RELAY_TRACE=<file>` appends each request's shape (roles,
block counts, marks, short hashes of the prefix's parts) and the API's
error bodies, never text or headers.

## Measured

One run each way on throwaway chats of 400 made-up notes (opt-chat's own
docs, shuffled differently per arm so they share no cache), Haiku 5.5 for
turns and compactions, effort low, the user's Claude Code setup on. Three
turns each, 75 s apart, each a long message that needs a compaction.
Steady-state turns, from the `[context ...]` line:

| per turn | ack (off) | relay (on) |
|---|---|---|
| requests | 2 | 1 |
| cache read | 32.4k + 32.4k | 35.9k |
| cache write | 9.1k | 0 |
| uncached input | 0 | 6.8k |

The off arm's 9.1k write is the rest of the view and the input, not read again by the next turn.
The relay sends it uncached, at the base input price, and (inferred, not
measured) Claude Code's own marks write it once a turn makes a second request.

Compactions over the same runs: 17 with the relay, averaging 20.2k read,
3.9k written and 2.5k uncached; 19 without, 31.5k read and 5.6k written.
Requests: 36 with the relay, 53 without, for three turns and their
compactions.

Small sample: one run per arm, different content, compaction counts that
depend on timing.

## Risks

- Claude Code's request layout is not an interface. It moved the
  environment block between a system message and the first user message
  from one run to the next. The relay handles both layouts it saw; a third
  one would go on unmarked, which costs cache, not correctness.
- The relay sees the OAuth token in transit. It forwards headers and
  never reads, logs or stores them.
- A relay that can't reach the API answers 502, which Claude Code
  retries like any network error. There is no per-call fallback to a
  direct connection.
- The "ok" message the relay inserts reads to the model as its own reply,
  as the ack's real one did.
